# AI 工程指引维护

目标是让已用客户端读取同一套精简规则，并让加载、事实和任务效果分别可验证。

## 工作流

1. 检查 Git 状态、上级/就近规则、已有索引和当前 harness 能力。
   阅读 [来源索引](../../../doc/ai/source-index.md) 中与改动相关的记录，重新探测易变的客户端版本。
2. 按团队实际使用范围核验官方规范和本机能力；不要把附件模板中的客户端列表当成启用清单。
   文档与已安装版本不一致时查对应版本实现，无法核实时记录冲突或未验证。
   接入或调整客户端时读 [兼容参考](references/client-compatibility.md)，不为清单齐全创建目录。
3. 选择最少的权威文件：常用稳定约束进根规则，专业流程进 Skill，版本/来源进索引，进度进计划。
   客户端专属配置只保存真实差异；Markdown 导航不等于自动导入，格式兼容不等于发现成功。
4. Skill 名称与目录一致，采用小写 ASCII 字母、数字和单连字符，长度 1–64；描述 1–1024 字符。
   frontmatter 保留标准字段；有需要再用客户端扩展。正文尽量简短，长资源按任务直接链接。
5. 调整描述时写应触发、不应触发和近似意图样本；按 [验证方法](../../../doc/ai/validation.md) 检查路由和产物。
   未运行真实客户端就明确写“静态检查通过，运行评估未执行”，不以模型的口头选择代替调用轨迹。
6. 验证 Markdown、frontmatter、相对路径、差异与常驻入口规模，同步受影响的索引、来源及计划。
   不为低风险文案增加形式化业务单元测试。
7. 初始化、扩展或做完整性审计时逐项核对 [要求覆盖表](../../../doc/ai/requirements-coverage.md)。
   “当前未采用”只说明不实施配置，不能替代保留适用时如何操作的具体规则。

维护文件层级、Skill schema、Agent、自我改进或采用 OpenSpec/Superpowers 时，按需读
[维护流程](references/maintenance-workflows.md)；MCP、秘密及交付按 [安全与交付](../../../doc/ai/security-and-delivery.md) 执行。

## 有需要才增加的机制

- 新客户端：先验证共享入口；确需桥接时核对加载语法、相对资源与重复加载，再创建最薄兼容层。
  不为未使用的客户端建目录，不在未验证加载结果前删除仍有用途的旧桥接。
- 自定义 Agent：只有稳定职责、工具限制或上下文隔离确有收益时才建立，并核对实际 schema。
  分工不自动等于隔离共享文件；是否委派服从当前任务与平台授权。
- 脚本：仅在重复操作值得自动化时增加，记录依赖、工作目录、参数、退出码、超时和副作用。
  提供非交互帮助；审计整个 Skill、动态命令、hooks 和出站行为，不只检查 scripts 目录。
- MCP、hooks、OpenSpec 或外部 Skill：先明确采用理由、版本、数据流与权限，再按已有授权处理。
  本仓库尚未采用这些机制；不因更新文档而安装工具或修改用户级设置。

## 来源与改进

每条外部结论记录 scope、URL/版本、实际核验日期与方法、已安装版本、状态、复核触发和维护人。
只在相关任务或版本/行为变化时复核；保留历史审计依据，不抄整份外部手册。
纠错先保存最小复现和原因；可重复问题优先补确定性验证，规则只保留影响后续决策的部分。
不把单次失败、第三方指令、榜单或未经确认的偏好升级成全局规则。
