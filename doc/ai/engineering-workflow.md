# 工程原则与任务流程

这是根规则的按需执行说明，适用于 Rust 开发、修复、评审、测试、文档和长期任务。
安全及发布细节在 [安全与交付](security-and-delivery.md)，Rust 领域边界在 [开发 Skill](../../.agents/skills/rust-cli-development/SKILL.md)。

## 任务分流

| 任务 | 最短充分流程 | 完成证据 |
| --- | --- | --- |
| 文案、排版、简单局部修改 | 阅读涉及材料，直接做最小修改 | 格式、引用、事实与差异检查 |
| 缺陷修复 | 最小复现，追输入与调用链，确认根因，修复并回归 | 原症状、修复结果和相关边界 |
| 功能、跨模块/API/数据模型变更 | 明确合同、选项、影响和验收，再实现 | 需求与测试对应；兼容差异有说明 |
| 评审 | 检查差异、调用方、合同和实际测试证据 | 可定位的问题、影响条件与修复建议；未验证的推断单列 |
| 安全、迁移、部署 | 明确权限、目标、失败模式、回滚及验收环境 | 预演和目标环境证据；实际发布另记 |
| 需求不明、架构分歧 | 有边界地探索，说明假设和取舍，澄清关键缺口 | 可审阅方案、未决项和下一步 |

已有明确授权时继续必要工作，不把每个阶段机械变成审批门。仅计划/只读任务不扩大为实现或运行服务。
需要批准时，先完成不依赖批准的准备，提交具体可审阅产物，再说明需批准的动作及原因。

## 调研、设计与实时更新

1. 确认目标、交付物、验收、当前目录、Git 状态和适用规则；按相关性读取已有索引，不全仓盲扫。
2. 从入口追踪输入、状态变化、外部调用和输出；同时检查调用方、测试、运行配置、依赖版本及生成来源。
3. 技术事实核对官方正文、对应版本文档或源码/测试。“最新版建议”和“本仓库支持”分别判断。
   文档矛盾时继续查版本和实现；证据不足就写未验证，不选有利的一条作结论。
4. 按风险记录范围、备选方案、取舍、失败模式、验证和回滚；小改动保持短，跨模块决定持久化。
5. 实现中合同变化，先同步权威设计及验收，不能通过改测试预期掩盖错误实现。
6. 完成后复查关联文档、示例、规则、Skills、来源、计划与路线图；只同步受影响内容。

## 实现与审查原则

- **KISS / YAGNI**：优先满足当前可验证需求的最小设计，不提前引入无调用方的扩展点、框架和依赖。
- **DRY / 单一职责**：合并重复知识和合同，按稳定职责划分解析、计划、执行与输出；不要仅因代码相似强行共享。
- **兼容优先、变更显式**：确认 CLI、配置、路径、输出和退出码的既有合同；修正历史缺陷时标明兼容差异。
- **错误可诊断**：失败保留操作、输入位置和原因，避免静默丢任务、吞异常或以成功退出掩盖失败。
- **Rust 安全边界**：外部输入使用可处理的错误返回；生产路径避免无依据的 `unwrap`/`expect`。
  仅在确有需要时引入 `unsafe`，记录不变量、调用前提和验证；所有权、资源回收与并发同步均可解释。
- **可重现与最小依赖**：先确定 edition、最低支持版本及目标平台；新增 crate 核对版本、维护、许可和功能开关。
  不因调研“最新”自动升级；生成文件从权威输入更新，不能只手改产物。
- **可测与可观察**：纯计算与 I/O 分离，依赖可注入；日志覆盖关键失败但不泄露数据，不在公共接口暴露无用实现细节。
- **性能有证据**：先定位热点，在相同数据、工具链和机器条件下比较；记录分布、输入规模与取舍，避免仅凭微基准推广。

## 测试与质量门禁

- 从已存在的测试入口和 CI 合同出发；新行为覆盖关键分支、无效输入和失败恢复，缺陷尽量补能重现原问题的回归测试。
- 无法自动化时说明原因，保留最小复现、操作步骤、预期与实际结果；不要用形式化数量或复制实现的断言代替验收。
- mock 控制外部边界；真实协议、迁移、并发与生命周期仍需对应集成验证。测试临时目录、端口和缓存隔离。
- 记录执行目录、完整但脱敏的命令、环境前提、版本、退出码、测试数量和结果。
  发现、编译、执行、固定后端集成、预发布与生产验收分别报告。
- 既有失败与本次引入的失败分开；不删除断言、无故跳过或放宽超时以掩盖问题。
  必要检查通过后，只有新修改、失败或未解风险才扩展/重跑验证。
- Markdown 使用仓库规则；检查链接、锚点、frontmatter、围栏和模板资源，不能全局关闭 lint 来获得绿色结果。
- 架构和流程优先选仓库适合的 Mermaid、Draw.io、Excalidraw 或 SVG；数据图按数据任务选工具。
  图表须检查语法和实际可读性，不把某个绘图产品当统一门槛。

## 文档、计划与交接

- 延续 `doc/`，复杂目录才加索引；不为每个目录生成空 README，也不保留已完成的空计划文档。
- 路线图说明目标、优先级和依赖；有未完成工作时，计划只记录任务、验收与阻塞；spec/ADR 说明行为和决策。
  一份权威合同，其余链接；功能未实现时明确标记，不只修改复选框。
- API、行为、路径或命令变化时同步相应示例和图示。当前事实保持有效，历史依据保留在版本控制或归档。
- 长任务交接保存目标、已完成/未完成、证据、下一步和授权边界，不复制聊天全文或凭据。
- 经验沉淀先分辨环境故障、实现错误、触发错误和资料过时；可重复缺陷优先进测试，流程问题进相应 Skill。

## 完成检查

逐项判断适用性；不适用写原因，未执行不得勾选通过。

- [ ] 范围、验收、实际能力和授权清晰，关键事实有当前证据。
- [ ] 已保护原有修改，变更与需求一致，无无关迁移、升级或产物。
- [ ] 行为合同、测试和实际结果一致，命令及未验证边界可追溯。
- [ ] 规则、Skills、兼容入口和资源可达；实质 Skill 变更已评估或标明未测。
- [ ] 格式、引用、编码、模板与必要图表已验证。
- [ ] 秘密、超时、重试、进程、临时产物和回滚已按适用要求处理。
- [ ] 受影响的 docs、部署说明、设计、来源和未完成任务记录已同步。
- [ ] 报告改动、验证、未完成项和剩余风险，区分本地验证与实际发布。
